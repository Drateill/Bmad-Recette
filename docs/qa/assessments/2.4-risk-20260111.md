## Critical Risks Requiring Immediate Attention

### 1. [SEC-001]: Console.error Exposes Internal Error Details

**Score: 9 (Critical)**
**Probability**: High (3) - Code currently contains console.error in production path
**Impact**: High (3) - Could expose S3 credentials, internal paths, or system architecture to attackers via logs

**Affected Components**:
- `apps/api/src/modules/storage/storage.service.ts:75`

**Details**: The StorageService.deleteFile() method uses console.error to log S3 deletion failures. This violates coding standards (requires structured logging with Pino) and could expose sensitive error details including AWS credentials, bucket structure, or internal system information in production logs.

**Mitigation**:
- IMMEDIATE: Replace console.error with proper Pino logger
- Add structured logging with sanitized error messages
- Ensure sensitive data (keys, URLs) are redacted from logs
- Implement log level controls for production

**Testing Focus**:
- Security audit of all logging statements
- Verify no sensitive data in log outputs
- Test log redaction mechanisms

**Status**: Must fix before production deployment

## High Risks

### 2. [SEC-002]: Missing Rate Limiting on File Upload Endpoints

**Score: 6 (High)**
**Probability**: Medium (2) - Common attack vector for public APIs
**Impact**: High (3) - DoS via resource exhaustion, storage cost attacks

**Affected Components**:
- `POST /api/recipes/:id/photos`

**Details**: No rate limiting implemented on photo upload endpoint. Attacker could repeatedly upload 10MB files to exhaust storage quota and S3 costs, or overload image processing (Sharp) to cause service degradation.

**Mitigation**:
- Add rate limiting middleware (e.g., 10 uploads per user per hour)
- Implement per-user storage quotas
- Add monitoring for unusual upload patterns
- Consider implementing upload costs in business logic

**Testing Focus**:
- Load testing with concurrent uploads
- Cost analysis for abuse scenarios
- Verify rate limit responses (429 Too Many Requests)

**Residual Risk**: Low with rate limiting + quotas implemented

---

### 3. [PERF-001]: No Caching Strategy for Recipe Photos

**Score: 6 (High)**
**Probability**: High (3) - Every recipe view will fetch photo metadata from database
**Impact**: Medium (2) - Degraded performance on high-traffic recipe pages

**Affected Components**:
- `RecipePhotosRepository.findByRecipeId()`
- Recipe detail and list views

**Details**: Photo metadata (s3Url, thumbnailUrl, isPrimary) is fetched from database on every request. No caching layer (Redis, in-memory) for frequently accessed recipes.

**Mitigation**:
- Implement caching for recipe photo metadata (TTL: 1 hour)
- Use CDN for S3 URLs (CloudFront mentioned in story as future enhancement)
- Add cache invalidation on photo upload/delete/primary change
- Consider edge caching for public recipes

**Testing Focus**:
- Load testing recipe list endpoint
- Measure database query load under concurrent users
- Verify cache invalidation works correctly

**Residual Risk**: Medium - Some database load remains for cache misses

## Medium Risks

### 4. [DATA-001]: No Transaction for S3 Upload + Database Create

**Score: 4 (Medium)**
**Probability**: Low (2) - Rare but possible race condition
**Impact**: Medium (2) - Orphaned files in S3 if database insert fails

**Affected Components**:
- `RecipePhotosService.uploadPhoto()` lines 58-79

**Details**: If S3 upload succeeds but database insertion fails (e.g., foreign key violation, connection timeout), files remain in S3 without database records (orphaned files). Over time, this wastes storage and incurs unnecessary costs.

**Mitigation**:
- Implement compensating transaction: delete S3 files if database insert fails
- Add S3 lifecycle policy to auto-delete orphaned files after 30 days (mentioned in story as future enhancement)
- Implement cleanup job to detect and remove orphaned files
- Consider two-phase commit pattern for critical data

**Current Mitigation**: Partial - Service catches errors but doesn't clean up S3 on failure

**Testing Focus**:
- Simulate database failures after S3 upload
- Verify cleanup mechanisms work
- Test S3 lifecycle policies in staging

**Residual Risk**: Low with cleanup job implemented

**Residual Risk**: Medium - Unit tests alone don't catch integration issues

### 6. [SEC-003]: No MIME Type Verification Beyond Extension

**Score: 4 (Medium)**
**Probability**: Medium (2) - Attackers commonly use MIME type spoofing
**Impact**: Medium (2) - Malicious files uploaded with image extensions

**Affected Components**:
- `ValidateImagePipe` - only checks mimetype from Multer

**Details**: Validation relies solely on client-provided MIME type. Attacker could upload malicious executable with image/jpeg MIME type. While Sharp will fail on non-images, this doesn't prevent all attacks (e.g., polyglot files).

**Current Mitigation**: Sharp metadata extraction will reject invalid images, but error happens after upload starts.

**Improvement**:
- Add magic number verification (check file header bytes)
- Use file-type library for robust MIME detection
- Implement virus scanning for production (ClamAV, VirusTotal API)

**Testing Focus**:
- Attempt to upload non-image files with spoofed MIME types
- Test polyglot files (valid image + embedded malicious payload)
- Verify Sharp rejection of malformed images

**Residual Risk**: Low - Sharp provides good secondary validation

## Low Risks

### 7. [OPS-001]: Missing Structured Logging for Upload Events

**Score: 3 (Low)**
**Probability**: Low (1) - Mentioned in story but not verified in code
**Impact**: High (3) - Difficult to debug issues, track usage, detect abuse

**Affected Components**:
- `RecipePhotosService.uploadPhoto()`
- `RecipePhotosService.deletePhoto()`

**Details**: Story mentions "Log photo upload events: userId, recipeId, fileSize, uploadDuration" but implementation doesn't show logging statements. This impacts:
- Debugging upload failures
- Tracking storage usage per user
- Detecting abuse patterns
- Audit trail for security

**Mitigation**:
- Add Pino structured logging for all photo operations
- Log: userId, recipeId, fileSize, uploadDuration, s3Key, operation (upload/delete/setPrimary)
- Add correlation IDs for tracing multi-step operations
- Implement log aggregation (ELK stack, CloudWatch)

**Testing Focus**:
- Verify log statements execute
- Check log format compliance
- Test log redaction of sensitive data

### 8. [DATA-002]: Primary Photo Auto-Promotion Logic Not Transactional

**Score: 2 (Low)**
**Probability**: Low (1) - Requires specific race condition during deletion
**Impact**: Medium (2) - Recipe could temporarily have no primary photo

**Affected Components**:
- `RecipePhotosService.deletePhoto()` lines 151-161

**Details**: When deleting primary photo, service promotes another photo in separate operation (not in transaction with delete). Race condition: if two delete requests arrive simultaneously, both could delete without promoting, leaving recipe with no primary photo.

**Current Mitigation**: Database-level cascade delete and application-level check

**Improvement**:
- Wrap delete + promote in transaction
- Add database constraint: at most one isPrimary per recipe
- Add retry logic for promotion failures

**Testing Focus**:
- Concurrent delete requests
- Verify exactly one primary photo after all operations

**Residual Risk**: Very Low - Rare race condition with low business impact
