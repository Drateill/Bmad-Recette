## Critical Issues

### 1. **Console.error in Production Code** (Security + Maintainability)
**File**: `apps/api/src/modules/storage/storage.service.ts:75`

**Risk**: Exposes internal error details (S3 keys, AWS credentials, bucket structure) in logs
**Impact**: Security vulnerability + violates coding standards
**Fix**: Replace with Pino structured logging with redaction

```typescript
// Current (BAD):
console.error(`Failed to delete S3 object: ${key}`, error);

// Should be (GOOD):
this.logger.error(
  { key: this.redactSensitiveData(key), errorCode: error.code },
  'Failed to delete S3 object'
);
```

**Effort**: ~30 minutes
**Priority**: CRITICAL - Must fix before production

---

### 2. **No Rate Limiting** (Security)
**Endpoints Affected**:
- `POST /api/recipes/:id/photos`

**Risk**: DoS attacks via resource exhaustion, storage cost attacks
**Impact**: Service degradation, unexpected AWS bills
**Fix**: Add NestJS throttler middleware

```typescript
@UseGuards(ThrottlerGuard)
@Throttle(10, 3600) // 10 uploads per hour
@Post()
async uploadPhoto(...)
```

**Effort**: ~2 hours (install package, configure, test)
**Priority**: HIGH - Required before public launch

---

### 3. **No Caching for Photo Metadata** (Performance)
**Query Affected**: `RecipePhotosRepository.findByRecipeId()`

**Risk**: Database bottleneck on high-traffic recipe pages
**Impact**: Slow response times (> 200ms) for recipe detail views
**Fix**: Add Redis caching layer

```typescript
async getRecipePhotos(recipeId: string): Promise<PhotoResponseDto[]> {
  const cacheKey = `recipe:${recipeId}:photos`;
  const cached = await this.cacheService.get(cacheKey);
  if (cached) return cached;

  const photos = await this.recipePhotosRepository.findByRecipeId(recipeId);
  await this.cacheService.set(cacheKey, photos, 3600); // 1 hour TTL
  return photos;
}
```

**Effort**: ~4 hours (setup Redis, implement caching, test invalidation)
**Priority**: MEDIUM - Can deploy without, but monitor performance

---

### 4. **Missing Integration Tests** (Maintainability)
**Coverage Gap**: No e2e tests for complete upload flow

**Risk**: Integration bugs between Controller → Service → S3 → Database not caught
**Impact**: Production bugs, regression risk on future changes
**Fix**: Add integration test suite using LocalStack or test S3 bucket

**Test Scenarios Needed**:
1. Upload valid image (JPEG, PNG, WebP) returns 201
2. Upload invalid file (>10MB) returns 400
3. Authorization: user cannot upload to another's recipe (403)
4. First photo marked as isPrimary=true
5. Delete primary photo auto-promotes next photo

**Effort**: ~6 hours (setup test infrastructure, write tests)
**Priority**: HIGH - Required for production confidence

## Detailed NFR Assessment

### Security: CONCERNS

#### Strengths ✓
- JWT authentication enforced on all endpoints (`@UseGuards(JwtAuthGuard)`)
- Recipe ownership verification before photo operations
- File validation: size (10MB), MIME type (JPEG, PNG, WebP)
- S3 public-read ACL appropriate for public recipe photos
- ConfigService used (no hardcoded credentials)

#### Weaknesses ✗
- **Console.error exposes internal details** (CRITICAL)
- **No rate limiting** on file upload endpoints (HIGH)
- MIME type validation only checks client-provided value (MEDIUM)
- No virus scanning for uploaded files (LOW - future enhancement)

#### Evidence
- Authorization checks: `RecipePhotosService:176-188`
- File validation: `ValidateImagePipe:16-31`
- S3 ACL: `StorageService:48` (appropriate for public photos)

#### Recommendations
1. Remove console.error, use Pino logger
2. Add rate limiting (10 uploads/hour per user)
3. Implement magic number MIME verification
4. Consider virus scanning for production

---

### Performance: CONCERNS

#### Strengths ✓
- Parallel processing: thumbnail + optimization via `Promise.all` (line 52-55)
- Parallel S3 uploads: original + thumbnail (line 58-69)
- Sharp library: Fast native image processing
- Progressive JPEG encoding for faster web loading
- Image optimization: max 1920px width, 85% quality

#### Weaknesses ✗
- **No caching layer** for photo metadata (HIGH)
- Every recipe view queries database for photos
- No CDN for S3 URLs (future enhancement noted)
- Sharp processing blocks Node.js event loop (acceptable for MVP)

#### Performance Targets (from architecture)
- API response time: < 200ms (target from architecture docs)
- Image processing: < 5 seconds for 10MB image (noted in story)

#### Current Estimates
- Database query: ~10-20ms (acceptable)
- Sharp processing: ~2-4s for 10MB image (acceptable)
- S3 upload: ~1-3s depending on network (acceptable)
- **Total upload time**: ~3-7 seconds (within target)

#### Recommendations
1. Add Redis caching for recipe photo metadata (TTL: 1 hour)
2. Implement CDN (CloudFront) for S3 URLs
3. Add cache invalidation on upload/delete/setPrimary
4. Monitor Sharp processing time in production

---

### Reliability: PASS ✓

#### Strengths ✓
- Comprehensive error handling in all service methods
- Try-catch blocks in ImageProcessingService (lines 18-30, 39-58)
- Graceful S3 delete failure handling (logs but doesn't throw)
- Transaction used for setPrimary (prevents orphaned primary flags)
- Parallel operations with `Promise.all` (faster + reliable)

#### Error Scenarios Covered
- Recipe not found: NotFoundException (line 182)
- User doesn't own recipe: ForbiddenException (line 187)
- Photo not found: NotFoundException (line 98, 128)
- Photo doesn't belong to recipe: NotFoundException (line 102)
- Invalid image buffer: BadRequestException via Sharp (ImageProcessingService)
- S3 upload failure: InternalServerErrorException (line 55-57)

#### Weaknesses ✗
- No retry logic for transient S3 failures (LOW - AWS SDK has built-in retries)
- No circuit breaker pattern (LOW - not needed for MVP)
- S3 delete failure silently logged (acceptable - idempotent operation)

#### Recommendations
1. Add retry logic with exponential backoff for S3 uploads (3 attempts)
2. Implement health check endpoint for S3 connectivity
3. Add monitoring for S3 operation success rates
