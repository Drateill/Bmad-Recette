# Story 2.5: Get Recipe Details API

## Status
Done

## Story
**As a** user,
**I want** to retrieve full recipe details by ID,
**so that** I can view a recipe with all ingredients, steps, tags, and photos.

## Acceptance Criteria

1. GET /api/recipes/:id endpoint returns complete recipe object
2. Response includes nested relationships: ingredients (with quantity, unit, name), steps (ordered by stepNumber), tags (with category), photos (with thumbnailUrl)
3. Authorization check: users can only access their own recipes (userId match)
4. 404 Not Found returned if recipe doesn't exist or belongs to another user
5. Response includes computed fields: totalTime (prepTime + cookTime), ingredientCount, stepCount
6. Efficient database query using joins (single query, not N+1)
7. Response format consistent with recipe list endpoint for frontend reusability

### Database Query Optimization

**Efficient Prisma Query** [Source: AC 6]
```typescript
async findById(recipeId: string): Promise<Recipe | null> {
  return await this.prisma.recipe.findUnique({
    where: { id: recipeId },
    include: {
      ingredients: {
        include: {
          ingredient: { // Include catalog reference
            select: {
              id: true,
              name: true,
              category: true,
              commonUnits: true,
            },
          },
        },
        orderBy: { sortOrder: 'asc' },
      },
      steps: {
        orderBy: { stepNumber: 'asc' },
      },
      tags: {
        include: {
          tag: {
            include: {
              category: true,
            },
          },
        },
      },
      photos: {
        orderBy: [
          { isPrimary: 'desc' },
          { uploadedAt: 'asc' },
        ],
      },
    },
  });
}
```

**Query Performance** [Source: AC 6, Prisma best practices]
- Single SQL query with JOINs (not N+1 queries)
- Use Prisma's `include` for eager loading relations
- Index on recipeId in all junction tables (already exists from Story 2.1, 2.2)
- Prisma generates optimized SQL with LEFT JOINs for optional relations

**Avoiding N+1 Problem** [Source: Prisma documentation]
- N+1 occurs when querying relations in loop: 1 query for recipe + N queries for each relation
- Solution: Use `include` to fetch all relations in single query
- Verify in Prisma logs: should see 1 SELECT with JOINs, not multiple SELECTs

### Authorization Pattern

**User Ownership Verification** [Source: AC 3, 4]
```typescript
async findById(recipeId: string, userId: string): Promise<Recipe> {
  const recipe = await this.recipesRepository.findById(recipeId);

  if (!recipe) {
    throw new NotFoundException('Recipe not found');
  }

  if (recipe.userId !== userId) {
    throw new ForbiddenException('You do not have access to this recipe');
  }

  return recipe;
}
```

**Error Response for Authorization Failure** [Source: AC 3, 4]
- 404 Not Found: Recipe doesn't exist OR user doesn't own it (don't reveal existence)
- Alternative: 403 Forbidden if you want to distinguish (less secure, reveals recipe exists)
- **PRD specifies**: Return 404 for both cases to prevent information leakage

### Performance Considerations

**Query Execution Time** [Source: PRD NFR3]

### Security Considerations

**Information Disclosure Prevention** [Source: AC 4]
- Don't reveal if recipe exists when user not authorized (return 404, not 403)
- Prevents attackers from enumerating valid recipe IDs
- Aligns with OWASP security best practices

**JWT Validation** [Source: Story 1.6 JWT implementation]
- JwtAuthGuard validates token signature and expiration
- Extract userId from verified token payload
- Never trust client-provided userId in request body or query params

#### 1. Security: Authorization Response Code (CRITICAL)

**Files Modified:**
- [apps/api/src/modules/recipes/recipes.service.ts](apps/api/src/modules/recipes/recipes.service.ts#L112-L116)

**Change:** Modified authorization check to return `404 Not Found` instead of `403 Forbidden` when user doesn't own recipe.

**Why:** AC 4 and Security Considerations explicitly require returning 404 for both "recipe not found" AND "unauthorized access" to prevent information disclosure. Returning 403 reveals that a recipe exists with that ID, allowing attackers to enumerate valid recipe IDs.

**How:**
- Combined the two separate checks into a single conditional: `if (!recipe || recipe.userId !== userId)`
- Both conditions now throw `NotFoundException` with message "Recipe not found"
- Removed `ForbiddenException` import and usage
- Updated all tests to expect 404 instead of 403
- Updated Swagger documentation to reflect security rationale

**Security Impact:** Prevents recipe ID enumeration attacks (OWASP A01:2021 – Broken Access Control)
