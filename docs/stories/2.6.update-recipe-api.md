# Story 2.6: Update Recipe API

## Status
Done

## Story
**As a** user,
**I want** to edit my existing recipes,
**so that** I can fix errors, add details, or adjust quantities.

## Acceptance Criteria

1. PUT /api/recipes/:id endpoint accepts partial updates to recipe fields
2. Supports updating: title, description, prepTime, cookTime, servings, ingredients, steps, tags
3. Ingredients update replaces entire array (delete existing + insert new) within transaction
4. Steps update replaces entire array (delete existing + insert new) within transaction
5. Tags update uses upsert logic (add missing, remove extras) for efficiency
6. updatedAt timestamp automatically set to current time
7. Authorization enforced: only recipe owner can update
8. Optimistic locking prevents concurrent update conflicts (version field or updatedAt check)
9. Returns 200 OK with updated recipe object, or 409 Conflict if concurrent modification detected

### Transaction-Based Update Strategy

**Why Full Replacement for Ingredients/Steps?** [Source: AC 3, 4]
- Simplifies client logic: send complete new array, backend handles diff
- Avoids complex partial update logic (which ingredient changed?)
- Cleaner database state: no orphaned records
- Easier to test: predictable behavior
- Trade-off: Slightly less efficient (deletes unchanged items), but simpler

**Atomic Transaction** [Source: AC 3, 4, 5, Prisma transactions]
```typescript
async update(recipeId: string, data: UpdateRecipeDto): Promise<Recipe> {
  return await this.prisma.$transaction(async (prisma) => {
    // 1. Update Recipe fields
    const recipe = await prisma.recipe.update({
      where: { id: recipeId },
      data: {
        ...(data.title && { title: data.title }),
        ...(data.description !== undefined && { description: data.description }),
        ...(data.prepTime && { prepTime: data.prepTime }),
        ...(data.cookTime && { cookTime: data.cookTime }),
        ...(data.servings && { servings: data.servings }),
        version: { increment: 1 },
      },
    });

    // 2. Replace ingredients if provided
    if (data.ingredients) {
      await prisma.recipeIngredient.deleteMany({ where: { recipeId } });
      await prisma.recipeIngredient.createMany({
        data: data.ingredients.map((ing, index) => ({
          recipeId,
          ingredientId: ing.ingredientId || null,
          ingredientName: ing.ingredientName,
          quantity: ing.quantity,
          unit: ing.unit,
          notes: ing.notes,
          sortOrder: ing.sortOrder ?? index + 1,
        })),
      });
    }

    // 3. Replace steps if provided
    if (data.steps) {
      await prisma.recipeStep.deleteMany({ where: { recipeId } });
      await prisma.recipeStep.createMany({
        data: data.steps.map((step, index) => ({
          recipeId,
          stepNumber: step.stepNumber ?? index + 1,
          instruction: step.instruction,
          duration: step.duration,
        })),
      });
    }

    // 4. Upsert tags if provided
    if (data.tagIds) {
      const existingTags = await prisma.recipeTag.findMany({
        where: { recipeId },
        select: { tagId: true },
      });
      const existingTagIds = existingTags.map((t) => t.tagId);

      const tagsToAdd = data.tagIds.filter((id) => !existingTagIds.includes(id));
      const tagsToRemove = existingTagIds.filter((id) => !data.tagIds.includes(id));

      if (tagsToRemove.length > 0) {
        await prisma.recipeTag.deleteMany({
          where: { recipeId, tagId: { in: tagsToRemove } },
        });
      }

      if (tagsToAdd.length > 0) {
        await prisma.recipeTag.createMany({
          data: tagsToAdd.map((tagId) => ({ recipeId, tagId })),
        });
      }
    }

    // 5. Fetch and return updated recipe with relations
    return await prisma.recipe.findUnique({
      where: { id: recipeId },
      include: {
        ingredients: { orderBy: { sortOrder: 'asc' } },
        steps: { orderBy: { stepNumber: 'asc' } },
        tags: { include: { tag: { include: { category: true } } } },
        photos: { orderBy: [{ isPrimary: 'desc' }, { uploadedAt: 'asc' }] },
      },
    });
  });
}
```

**Rollback on Failure** [Source: Prisma transactions]
- If ANY operation fails, entire transaction rolls back
- Database remains consistent (no partial updates)
- Prisma handles rollback automatically

### Optimistic Locking Strategy

**Why Optimistic Locking?** [Source: AC 8, 9]
- Prevents lost updates when two users edit same recipe concurrently
- User A and User B both fetch recipe (version 1)
- User A saves first: version increments to 2
- User B tries to save: version mismatch detected (expects 1, found 2)
- User B receives 409 Conflict, must refresh and retry

**Version Field Approach** [Source: architecture/data-models.md, AC 8]
```typescript
// Client includes expectedVersion in update request
const updateDto = {
  title: 'New Title',
  expectedVersion: 1, // Version from GET request
};

// Server checks version before update
const recipe = await prisma.recipe.findUnique({ where: { id: recipeId } });
if (recipe.version !== updateDto.expectedVersion) {
  throw new ConflictException('Recipe was modified by another user');
}

// Update and increment version
await prisma.recipe.update({
  where: { id: recipeId },
  data: {
    title: updateDto.title,
    version: { increment: 1 },
  },
});
```

**Alternative: updatedAt Timestamp Approach** [Source: simpler alternative]
- Client includes lastUpdatedAt from GET request
- Server checks if recipe.updatedAt > lastUpdatedAt
- If newer: throw ConflictException
- Simpler, but less precise (race condition within same millisecond)

**MVP Recommendation**: Use version field (more robust, already exists in schema)

### Partial Update Handling

**Only Update Provided Fields** [Source: AC 1]
```typescript
// Build dynamic update object
const updateData: any = {};
if (data.title !== undefined) updateData.title = data.title;
if (data.description !== undefined) updateData.description = data.description;
if (data.prepTime !== undefined) updateData.prepTime = data.prepTime;
// ... etc

await prisma.recipe.update({
  where: { id: recipeId },
  data: updateData,
});
```

**Distinguishing Null vs Undefined**
- `description: null` → Set description to null (clear description)
- `description: undefined` → Don't change description (omitted from request)
- Important: Use `!== undefined` checks, not truthiness

### Error Handling

**HTTP Status Codes** [Source: AC 9, REST best practices]
- 200 OK: Recipe updated successfully
- 400 Bad Request: Invalid input (validation failed)
- 401 Unauthorized: No JWT token or invalid token
- 403 Forbidden: User doesn't own recipe
- 404 Not Found: Recipe doesn't exist
- 409 Conflict: Optimistic locking detected concurrent modification
- 500 Internal Server Error: Database error or unexpected failure

**Prisma Error Handling**
- P2025: Record not found → 404 Not Found
- P2003: Foreign key constraint violation (invalid tagId or ingredientId) → 400 Bad Request
- P2002: Unique constraint violation (unlikely here) → 409 Conflict

```typescript
it('should detect concurrent modifications with optimistic locking', async () => {
  // User A fetches recipe (version 1)
  const recipeA = await request(app.getHttpServer())
    .get(`/api/recipes/${testRecipe.id}`)
    .set('Authorization', `Bearer ${userAToken}`)
    .expect(200);

  // User B fetches recipe (version 1)
  const recipeB = await request(app.getHttpServer())
    .get(`/api/recipes/${testRecipe.id}`)
    .set('Authorization', `Bearer ${userBToken}`) // Same user, different session
    .expect(200);

  // User A updates successfully (version becomes 2)
  await request(app.getHttpServer())
    .put(`/api/recipes/${testRecipe.id}`)
    .set('Authorization', `Bearer ${userAToken}`)
    .send({ title: 'Updated by A', expectedVersion: 1 })
    .expect(200);

  // User B tries to update with stale version (expects 1, but it's now 2)
  await request(app.getHttpServer())
    .put(`/api/recipes/${testRecipe.id}`)
    .set('Authorization', `Bearer ${userBToken}`)
    .send({ title: 'Updated by B', expectedVersion: 1 })
    .expect(409); // Conflict
});
```

### Performance Considerations

**Transaction Overhead** [Source: Prisma performance]
- Transactions add slight overhead (~10-20ms)
- Trade-off: Consistency vs speed (consistency wins for data integrity)
- Single transaction better than multiple sequential queries

**Array Replacement Performance**
- Delete + CreateMany for 10 ingredients: ~50-100ms
- Acceptable for recipe updates (not frequent operation)
- Alternative (differential updates) more complex, marginal benefit

### Security Considerations

**Input Sanitization** [Source: AC validation, OWASP best practices]
- Escape HTML in description to prevent XSS
- Validate all numeric fields (no negative times or servings)
- Validate UUIDs for tagIds and ingredientIds
- Trim whitespace to prevent formatting issues

**Authorization Enforcement** [Source: AC 7]
- Always verify recipe ownership before update
- Use JWT userId, never trust client-provided userId
- Return 403 Forbidden (or 404) if unauthorized
