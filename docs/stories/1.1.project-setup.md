## Dev Notes

### Architecture Context
This story establishes the foundational monorepo structure for the BMad Recette project, which will house web, mobile, and backend applications with shared code packages.

[Source: architecture/high-level-architecture.md#repository-structure]

### Monorepo Structure
**Required Directory Structure:**
```
bmad-recette/
├── apps/
│   ├── api/          # NestJS backend application
│   ├── web/          # React web application
│   └── mobile/       # React Native (Expo) mobile application
├── packages/
│   ├── shared/       # Shared TypeScript types, utilities, constants
│   ├── ui/           # Shared UI components (React + React Native compatible)
│   └── config/       # Shared configs (ESLint, TypeScript, Jest)
├── scripts/          # Build, deploy, and seed scripts
├── docs/             # Documentation (PRD, architecture, etc.)
├── turbo.json        # Turborepo configuration
└── package.json      # Root package.json
```

**Rationale:**
- `apps/`: Each deployable application isolated with its own package.json and build config
- `packages/shared/`: Critical for type safety—API contracts (DTOs), business logic utilities, validation schemas shared across all apps
- `packages/ui/`: React components designed for cross-platform compatibility (React + React Native via react-native-web patterns where possible)
- `packages/config/`: DRY principle for linting, TypeScript, testing configs
- Turborepo caching: Shared packages cached globally, only rebuild what changed
- Workspace dependencies: `apps/web` imports from `@bmad/shared`, `apps/api` imports from `@bmad/shared` for type-safe API contracts

[Source: architecture/high-level-architecture.md#repository-structure]

### Technology Stack
**Monorepo Tool:** Turborepo 2.0+
- Incremental builds, intelligent caching, parallel execution
- Simple configuration
- Vercel-native integration

**Language:** TypeScript 5.3+ for all packages
- Type-safe web and mobile development
- Industry standard for large React codebases
- Catches bugs at compile time
- Enables shared types across monorepo
- Excellent IDE support

**Version Strategy:**
- All versions locked in package.json using exact versions (no `^` or `~`)
- Major version upgrades require architecture review
- Security patches applied automatically via Dependabot

[Source: architecture/tech-stack.md#technology-stack-table]

### Coding Standards to Apply
**Critical Fullstack Rules:**
- **Type Sharing:** Always define types in `packages/shared/types` and import from `@bmad/shared/types`
- **Environment Variables:** Access through typed config objects, never `process.env` directly

**Naming Conventions:**
- Components: PascalCase (e.g., `UserProfile.tsx`)
- Hooks: camelCase with 'use' prefix (e.g., `useAuth.ts`)
- API Routes: kebab-case (e.g., `/api/user-profile`)
- Database Tables: snake_case (e.g., `user_profiles`)

[Source: architecture/coding-standards.md#critical-fullstack-rules]

### Package Manager
Use **npm** or **yarn** workspaces (both compatible with Turborepo). The root package.json should define workspaces pointing to `apps/*` and `packages/*`.

### Pre-commit Hook Configuration
Configure Husky + lint-staged to run:
- ESLint on all `.ts`, `.tsx`, `.js`, `.jsx` files
- Prettier on all staged files
- TypeScript type checking (optional but recommended)

This ensures code quality is enforced automatically before commits.

### Testing

This story focuses on infrastructure setup, so testing is limited to:
- Verifying build commands work across all packages
- Ensuring linting and type-checking pass
- Testing that pre-commit hooks properly block invalid code

[Source: architecture/testing-strategy.md#testing-pyramid]

#### Test Organization
No automated tests required for this story beyond the verification that:
1. `npm run build` succeeds across all packages
2. `npm run lint` passes across all packages
3. `npm run test` runs (even if no tests exist yet)
4. Pre-commit hooks block commits with linting errors

Future stories will implement:

- **Backend Tests:** Unit tests for services and repositories, Integration tests for API endpoints

[Source: architecture/testing-strategy.md#test-organization]
