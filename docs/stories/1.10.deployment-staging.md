# Story 1.10: Deployment to Staging Environment

## Status
Approved

## Story
**As a** developer,
**I want** the application deployed to a staging environment accessible via URL,
**so that** stakeholders can test the authentication flow and verify the foundation is production-ready.

## Acceptance Criteria
1. Backend API deployed to Railway (or Render) with PostgreSQL and Redis provisioned
2. Web app deployed to Vercel with environment variables configured (API base URL)
3. Mobile app builds successfully for iOS (TestFlight) and Android (internal test track) - manual deployment for MVP
4. Staging environment accessible at predictable URLs (e.g., api-staging.bmadrecette.com, app-staging.bmadrecette.com)
5. Database migrations run automatically on deployment via CI/CD pipeline
6. Health-check endpoint verified returning 200 OK on staging
7. Staging environment uses separate database from production (staging data isolated)
8. Basic monitoring configured: Sentry for error tracking, uptime monitoring via health-check endpoint

### Database Migration Strategy
**Prisma Migrations on Deploy:** [Source: AC 5]
```bash
# Run migrations automatically on Railway deployment
npx prisma migrate deploy
```

**Migration Command:**
- `prisma migrate deploy`: Applies pending migrations (production-safe, no prompts)
- `prisma migrate dev`: Interactive, for development only (NOT for production/staging)

**Process:**
1. Developer creates migration locally: `npx prisma migrate dev --name add_users_table`
2. Migration file committed to git: `apps/api/prisma/migrations/TIMESTAMP_add_users_table/migration.sql`
3. Push to GitHub triggers Railway deployment
4. Railway runs: `npm run migrate:deploy` (which runs `prisma migrate deploy`)
5. Prisma applies migrations that haven't been applied yet
6. Backend starts with updated schema

**Safety:**
- Migrations are idempotent (can run multiple times safely)
- Prisma tracks applied migrations in `_prisma_migrations` table
- If migration fails, deployment stops (prevents broken state)

[Source: Prisma documentation, [deployment-architecture.md](../architecture/deployment-architecture.md#deployment-strategy)]

on:
  push:
    branches: [main]

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint
      - run: npm run type-check
      - run: npm run test -- --coverage

  deploy-backend:
    needs: test
    runs-on: ubuntu-latest

      - name: Trigger Railway Deployment

    needs: test
    runs-on: ubuntu-latest

      # Optional: Use Vercel CLI to wait for deployment

### Security Considerations
**Staging Security:**
- Use separate OAuth credentials for staging (prevents production abuse)
- Use different JWT secrets for staging (isolate from production)
- Restrict staging to internal testers (no public access)
- Enable HTTPS only (Railway and Vercel enforce automatically)
- Isolate staging database (never share with production)
- Rotate staging credentials periodically

**Production Readiness:**
- This story establishes staging environment (NOT production)
- Production deployment will be separate story in future sprint
- Production requires: Custom domain, production OAuth, higher resource limits, backup strategy
