# Story 2.8: Recipe List & Filtering API

## Status
Draft

## Story
**As a** user,
**I want** to view my recipe library with filtering and sorting options,
**so that** I can find recipes quickly based on various criteria.

## Acceptance Criteria

1. GET /api/recipes endpoint returns paginated list of user's recipes
2. Query parameters supported: page, limit (default 20, max 100), sortBy (title, createdAt, prepTime), sortOrder (asc, desc)
3. Filtering by tags: ?tagIds=1,2,3 returns recipes matching ANY of the specified tags
4. Filtering by search query: ?q=chicken searches recipe title, description, and ingredient names (full-text search)
5. Filtering by time: ?maxTotalTime=30 returns recipes with totalTime ≤ 30 minutes
6. Each recipe in list includes: id, title, description, prepTime, cookTime, servings, primaryPhoto (thumbnail), tagIds, rating
7. Response includes pagination metadata: total, page, pageSize, totalPages
8. Efficient queries with proper indexing (avoid table scans on large datasets)

### Prisma Query Construction

**Base Query with Filters** [Source: AC 2, 3, 4, 5]
```typescript
async findAll(userId: string, filters: RecipeFilterDto): Promise<Recipe[]> {
  const where: Prisma.RecipeWhereInput = {
    userId,
    AND: [],
  };

  // Tag filtering (OR logic)
  if (filters.tagIds && filters.tagIds.length > 0) {
    where.AND.push({
      tags: {
        some: {
          tagId: { in: filters.tagIds },
        },
      },
    });
  }

  // Search query (title, description, ingredient names)
  if (filters.q) {
    where.AND.push({
      OR: [
        { title: { contains: filters.q, mode: 'insensitive' } },
        { description: { contains: filters.q, mode: 'insensitive' } },
        {
          ingredients: {
            some: {
              ingredientName: { contains: filters.q, mode: 'insensitive' },
            },
          },
        },
      ],
    });
  }

  // Time filtering (computed field)
  // Note: Prisma doesn't support computed fields in where clause
  // Workaround: Filter in-memory after fetch or use raw SQL
  // For MVP: Fetch without time filter, then filter in-memory

  const recipes = await this.prisma.recipe.findMany({
    where,
    include: {
      photos: {
        where: { isPrimary: true },
        select: { id: true, thumbnailUrl: true },
      },
      tags: {
        select: { tagId: true },
      },
    },
    orderBy: { [filters.sortBy]: filters.sortOrder },
    skip: (filters.page - 1) * filters.limit,
    take: filters.limit,
  });

  // Filter by maxTotalTime in-memory (if provided)
  if (filters.maxTotalTime) {
    return recipes.filter(r => (r.prepTime + r.cookTime) <= filters.maxTotalTime);
  }

  return recipes;
}
```

### Tag Filtering Logic

**OR Logic for Tags** [Source: AC 3]
- User selects tags: "Vegetarian", "Quick", "Dinner"
- Return recipes with ANY of these tags (not all three)
- SQL equivalent: `WHERE recipeId IN (SELECT recipeId FROM recipe_tags WHERE tagId IN (...))`

**Prisma Implementation**
```typescript
{
  tags: {
    some: { // At least one tag matches
      tagId: { in: filters.tagIds },
    },
  },
}
```

**Performance Consideration** [Source: AC 8]
- RecipeTags table has index on recipeId and tagId (from Story 2.2)
- Subquery efficient for up to 100k recipes
- For 1M+ recipes, consider materialized view or denormalized tag array

### Full-Text Search Implementation

**MVP Approach: ILIKE Queries** [Source: AC 4]
- Simple pattern matching: `WHERE title ILIKE '%chicken%'`
- Case-insensitive search
- Performance: Acceptable for <10k recipes, slower for larger datasets
- No relevance ranking

**V2 Enhancement: PostgreSQL Full-Text Search** [Source: PostgreSQL tsvector]
- Add tsvector column: `searchVector tsvector`
- Update on recipe save: `searchVector = to_tsvector('english', title || ' ' || description)`
- Query: `WHERE searchVector @@ to_tsquery('chicken')`
- Benefits: Faster, relevance ranking, stemming (searches "chickens" finds "chicken")

**MVP Recommendation**: Use ILIKE for simplicity, upgrade to tsvector in V2 if performance issue

### Time Filtering Challenge

**Problem** [Source: AC 5, Prisma limitations]
- `totalTime = prepTime + cookTime` is computed field
- Prisma doesn't support `WHERE (prepTime + cookTime) <= 30` directly

**Solutions**
1. **In-Memory Filtering** (MVP approach):
   - Fetch recipes without time filter
   - Filter in JavaScript: `recipes.filter(r => r.prepTime + r.cookTime <= maxTotalTime)`
   - Trade-off: Fetches more data than needed, but simple

2. **Raw SQL** (more efficient):
   ```sql
   SELECT * FROM recipes
   WHERE userId = ? AND (prepTime + cookTime) <= ?
   ORDER BY createdAt DESC
   LIMIT 20 OFFSET 0
   ```

3. **Denormalized totalTime Column** (best performance):
   - Add `totalTime` column to recipes table
   - Update on recipe save: `totalTime = prepTime + cookTime`
   - Query: `WHERE totalTime <= 30`
   - Trade-off: Data duplication, must keep in sync

**MVP Recommendation**: In-memory filtering (simplest), upgrade to denormalized column in V2 if needed

### Pagination Strategy

**Offset-Based Pagination** [Source: AC 7]
- Skip: (page - 1) * limit
- Take: limit
- Simple to implement, familiar to users
- Trade-off: Performance degrades on deep pages (page 1000+)

**Cursor-Based Pagination** [Source: V2 enhancement]
- Use cursor (e.g., lastSeenId) instead of page number
- More efficient for infinite scroll
- V2 consideration for mobile app

**Pagination Metadata Calculation**
```typescript
const total = await this.recipesRepository.count(userId, filters);
const totalPages = Math.ceil(total / filters.limit);

return {
  data: recipes,
  pagination: {
    page: filters.page,
    pageSize: filters.limit,
    total,
    totalPages,
  },
};
```

### Performance Targets

**Query Performance** [Source: PRD NFR3, AC 8]
- Recipe list (<100 results): <200ms
- Recipe list with filters: <500ms
- Search query: <1s
- Target: 95th percentile response time

**Optimization Techniques**
- Use indexes for all WHERE and ORDER BY clauses
- Limit included relations (only primary photo, not all photos)
- Use select to fetch only needed fields (reduce payload size)
- Cache frequent queries in Redis (optional V2 enhancement)

### Response Payload Size

**List vs Detail View** [Source: AC 6]
- List view: Minimal data per recipe (~500 bytes)
  - Includes: id, title, description, times, primary photo thumbnail, tag IDs, rating
  - Excludes: ingredients, steps, all photos
- Detail view (Story 2.5): Complete recipe (~5-10KB)
  - Includes: all ingredients, steps, photos, full tags

**Pagination Benefit**
- Page of 20 recipes: ~10KB payload
- Without pagination (1000 recipes): ~500KB payload (too large for mobile)
