## Dev Notes

### Architecture Context
This story establishes the foundational NestJS backend API infrastructure for BMad Recette, including database connectivity (PostgreSQL), caching/session layer (Redis), security middleware, and observability (health checks, structured logging).

**Key Architectural Decisions**:
- **Monolithic API**: Single NestJS backend with modular internal structure
- **Database**: PostgreSQL 15+ for primary data storage
- **Cache/Session**: Redis 7+ for session management and future caching needs
- **Migrations**: Database schema versioning for controlled evolution

[Source: docs/prd.md - Technical Assumptions - Service Architecture]

### Technology Stack

**Backend Framework**: NestJS (latest stable)
- Enterprise-grade structure with dependency injection
- Modular architecture enables future microservices extraction
- Built-in support for TypeScript, validation, and testing
- Excellent ecosystem for REST APIs

**Database**: PostgreSQL 15+
- JSONB support for flexible metadata (tags, etc.)
- Built-in full-text search capabilities
- Strong ACID guarantees
- Wide cloud hosting support

**Migration Tool**: Prisma (recommended) or TypeORM
- **Prisma**: Better developer experience, modern ORM, excellent type safety
- **TypeORM**: More traditional ORM, integrated with NestJS ecosystem
- Choose based on team preference (Prisma recommended for new projects)

**Cache/Session**: Redis 7+
- In-memory data structure store
- Session management for JWT refresh tokens
- Future use: rate limiting, real-time sync coordination

**Logging**: Pino
- High-performance JSON logger
- NestJS compatible via nestjs-pino
- Structured logging for production observability

[Source: docs/prd.md - Technical Assumptions - Backend Technology Stack]

### Security Headers with Helmet.js

Configure Helmet.js to set the following security headers:
- `Content-Security-Policy`: Prevent XSS attacks
- `X-Frame-Options`: Prevent clickjacking
- `X-Content-Type-Options`: Prevent MIME sniffing
- `Strict-Transport-Security`: Force HTTPS
- `X-DNS-Prefetch-Control`: Control DNS prefetching

Use Helmet defaults in development, customize for production based on frontend requirements.

### Health Check Endpoint Specification

**Endpoint**: `GET /api/health`

**Response Format**:
```json
{
  "status": "ok",
  "timestamp": "2026-01-06T10:30:00.000Z",
  "version": "0.1.0",
  "services": {
    "database": "healthy",
    "redis": "healthy"
  }
}
```

**Status Codes**:
- `200 OK`: All services healthy
- `503 Service Unavailable`: One or more services degraded/unhealthy (optional enhancement)

For MVP, basic health check is sufficient. Service-level checks can be added later for better observability.

### Connection Pooling Best Practices

**PostgreSQL**: Configure connection pooling to stay within free tier limits
- Development: 5 max connections
- Production: Adjust based on hosting provider (e.g., Railway: 100 max)

**Redis**: Single connection sufficient for MVP
- Connection pooling can be added in V2 if needed

[Source: docs/prd.md - Technical Assumptions - Cost Constraints & Optimization]

### Error Handling

Implement graceful degradation:
- **Database unavailable**: Log error, return 503 from health check, prevent app startup
- **Redis unavailable**: Log warning, allow app to start (sessions won't work but app doesn't crash)

Use NestJS exception filters for consistent error response format.

### Coding Standards to Apply

**Critical Backend Rules**:
- **Environment Variables**: Access through typed config objects, NEVER `process.env` directly
- **Error Handling**: Always use custom exception filters for consistent API responses
- **Validation**: Use class-validator for all DTOs
- **Logging**: Use dependency-injected logger, never console.log

**Naming Conventions**:
- Modules: PascalCase (e.g., `HealthModule`)
- Controllers: PascalCase with `Controller` suffix (e.g., `HealthController`)
- Services: PascalCase with `Service` suffix (e.g., `DatabaseService`)
- API Routes: kebab-case (e.g., `/api/health`, `/api/user-profile`)
- Database Tables: snake_case (e.g., `users`, `recipe_tags`)

### Docker Compose for Local Development

Create `docker-compose.yml` in root for local PostgreSQL and Redis:

```yaml
version: '3.8'
services:
  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: bmad
      POSTGRES_PASSWORD: dev_password
      POSTGRES_DB: bmad_recette_dev
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data

volumes:
  postgres_data:
  redis_data:
```

**Usage**: `docker-compose up -d` to start, `docker-compose down` to stop

This allows developers to quickly spin up dependencies without manual installation.
