## Dev Notes

### Architecture Context
This story establishes the automated quality gates and deployment pipeline for the BMad Recette project. The CI/CD system ensures code quality through automated testing and enables rapid, reliable deployments to staging and production environments.

**Key Principles**:
- **Shift-left testing**: Catch issues early in development cycle
- **Automated quality gates**: No manual intervention required for standard checks
- **Fast feedback loops**: CI runs complete in under 5 minutes
- **Reproducible builds**: Same code produces same artifacts every time

[Source: docs/prd.md - Technical Assumptions - Development Workflow]

### GitHub Actions Workflow Strategy

**Two Primary Workflows**:

1. **PR Validation** (`pr-validation.yml`):
   - Triggers: On every push to any branch, on PR creation/update
   - Purpose: Validate code quality before merge
   - Jobs: lint, type-check, test (with coverage)
   - Failure: Blocks PR merge via required status checks

2. **Staging Deployment** (`deploy-staging.yml`):
   - Triggers: On merge to main branch
   - Purpose: Automatically deploy to staging environment
   - Jobs: build, deploy-api, deploy-web
   - Failure: Send notification, rollback to previous version

**Future Workflows** (not in this story):
- Production deployment (manual approval required)
- Nightly E2E tests (Playwright/Detox)
- Dependency updates (Dependabot auto-merge for minor/patch)

[Source: docs/prd.md - Technical Assumptions - CI/CD Integration]

### PR Validation Workflow Structure

**Workflow File**: `.github/workflows/pr-validation.yml`

```yaml
name: PR Validation

on:
  push:
    branches-ignore:
      - main
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  install:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - uses: actions/cache@v3
        with:
          path: node_modules
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}

  lint:
    needs: install
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint

  type-check:
    needs: install
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run type-check

  test:
    needs: install
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run test -- --coverage
      - uses: codecov/codecov-action@v3
        with:
          fail_ci_if_error: true
```

**Key Features**:
- Parallel jobs (lint, type-check, test run concurrently)
- npm cache for faster installs
- Shared install step (cached node_modules)
- Coverage upload to Codecov (optional: can use Coveralls or GitHub native)

### Test Coverage Configuration

**Jest Configuration** (add to `jest.config.js` or `package.json`):

```javascript
module.exports = {
  collectCoverageFrom: [
    'apps/**/*.{js,jsx,ts,tsx}',
    'packages/**/*.{js,jsx,ts,tsx}',
    '!**/*.d.ts',
    '!**/node_modules/**',
    '!**/*.config.{js,ts}',
  ],
  coverageThreshold: {
    global: {
      branches: 70,
      functions: 70,
      lines: 70,
      statements: 70,
    },
  },
  coverageReporters: ['text', 'lcov', 'json-summary'],
};
```

**Coverage Enforcement**:
- 70% threshold for branches, functions, lines, statements
- CI fails if new code drops coverage below threshold
- Coverage report uploaded to Codecov for PR comments

**Optional Enhancement**: Use `jest-coverage-comment` GitHub Action to post coverage comparison on PRs.

### Staging Deployment Workflow Structure

**Workflow File**: `.github/workflows/deploy-staging.yml`

```yaml
name: Deploy to Staging

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v3
        with:
          name: build-artifacts
          path: |
            apps/*/dist
            apps/*/build

  deploy-api:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v3
        with:
          name: build-artifacts
      - name: Deploy to Railway
        env:
          RAILWAY_TOKEN: ${{ secrets.RAILWAY_TOKEN }}
        run: |
          # Railway deployment command
          # Or Render deployment command
          echo "Deploy API to staging"

  deploy-web:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel
        env:
          VERCEL_TOKEN: ${{ secrets.VERCEL_TOKEN }}
          VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
          VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}
        run: |
          npx vercel --prod --token=$VERCEL_TOKEN
```

**Important**: Actual deployment commands depend on hosting provider choice (Railway vs Render for API, Vercel for web). This will be finalized in Story 1.10 (Deployment to Staging Environment).

### Build Caching Strategy

**npm Dependencies Cache**:
```yaml
- uses: actions/cache@v3
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
```

**Turborepo Remote Caching** (optional, significant speedup):
```yaml
- name: Configure Turborepo cache
  run: |
    npx turbo login --token=${{ secrets.TURBO_TOKEN }}
    npx turbo link
```

**Expected CI Performance**:
- Without cache: ~5-7 minutes
- With npm cache: ~3-4 minutes
- With Turborepo remote cache: ~1-2 minutes (only rebuild changed packages)

**Cache Invalidation**: Automatic when package-lock.json changes

### Branch Protection Rules

Configure in GitHub: Settings > Branches > Branch protection rules for `main`:

**Required Settings**:
- ✅ Require a pull request before merging
- ✅ Require approvals: 1 (or 0 for solo development)
- ✅ Require status checks to pass before merging
  - Required checks: `lint`, `type-check`, `test`
- ✅ Require branches to be up to date before merging
- ✅ Do not allow bypassing the above settings (even for admins)

**Optional Settings**:
- ✅ Require conversation resolution before merging
- ✅ Require linear history (no merge commits, use squash or rebase)
- ❌ Require signed commits (optional, adds friction)

**Rationale**: Prevents broken code from reaching main branch, ensures all code passes quality gates.
