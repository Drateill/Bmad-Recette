# Story 1.6: OAuth Authentication (Google & Apple)

## Status
Done

## Story
**As a** new or existing user,
**I want** to sign in using my Google or Apple account,
**so that** I can access the app quickly without managing another password.

## Acceptance Criteria
1. Passport.js configured with passport-google-oauth20 and passport-apple strategies
2. GET /api/auth/google endpoint initiates OAuth flow, callback at /api/auth/google/callback
3. GET /api/auth/apple endpoint initiates OAuth flow, callback at /api/auth/apple/callback
4. On successful OAuth callback, user created or retrieved from database using OAuth provider ID
5. New OAuth users have auto-generated profile with email from OAuth provider (if available)
6. OAuth login returns same JWT token structure as email/password login (access + refresh tokens)
7. Users can link multiple OAuth providers to same account (email as unique key)
8. OAuth configuration uses environment variables for client IDs and secrets

## Dev Notes

### Architecture Context

This story implements OAuth 2.0 authentication with Google and Apple, providing users a passwordless login option. OAuth integration uses Passport.js strategies and follows the standard authorization code flow. The implementation supports both new user creation and account linking for existing users.

**Key Architectural Principles:**
- Account linking via email as unique identifier
- OAuth users can exist without passwords (passwordHash = null)
- Multiple OAuth providers can be linked to a single account
- Same JWT token structure as email/password login for consistency
- Secure token exchange with httpOnly cookies

### API Specification

**Google OAuth Endpoints:**

1. **Initiate Google OAuth Flow**
   - Endpoint: GET /api/auth/google
   - Response: 302 Redirect to Google authorization URL
   - User sees Google consent screen

2. **Google OAuth Callback**
   - Endpoint: GET /api/auth/google/callback
   - Query Params: code (from Google), state (optional)
   - Response: 302 Redirect to frontend with access token
   - Redirect URL: `https://app.bmadrecette.com/auth/success?token=<accessToken>`
   - Cookie: refreshToken (httpOnly, secure, sameSite)

**Apple OAuth Endpoints:**

1. **Initiate Apple OAuth Flow**
   - Endpoint: GET /api/auth/apple
   - Response: 302 Redirect to Apple authorization URL
   - User sees Apple consent screen

2. **Apple OAuth Callback**
   - Endpoint: GET /api/auth/apple/callback (or POST depending on Apple config)
   - Query/Body Params: code (from Apple), user (optional, only on first login)
   - Response: 302 Redirect to frontend with access token
   - Cookie: refreshToken (httpOnly, secure, sameSite)

**OAuth Response Structure** (via redirect URL):
```
GET https://app.bmadrecette.com/auth/success?token=<accessToken>

Cookie: refreshToken=<jwt_token>; HttpOnly; Secure; SameSite=Strict; Path=/api/auth; Max-Age=604800
```

### OAuth Flow Diagram

```
1. User clicks "Sign in with Google" on frontend
   ↓
2. Frontend redirects to: GET /api/auth/google
   ↓
3. Backend redirects to: https://accounts.google.com/o/oauth2/v2/auth?client_id=...
   ↓
4. User authorizes on Google consent screen
   ↓
5. Google redirects to: GET /api/auth/google/callback?code=<auth_code>
   ↓
6. Backend (GoogleStrategy):
   - Exchanges code for access token with Google
   - Fetches user profile from Google
   - Validates and extracts: email, firstName, providerId
   ↓
7. Backend (AuthService.handleOAuthLogin):
   - Check if OAuth account exists (findByOAuthProvider)
   - If not, check if email exists (findByEmail)
   - Create new user OR link OAuth to existing user
   - Generate JWT tokens (access + refresh)
   - Store refresh token in Redis
   ↓
8. Backend redirects to: https://app.bmadrecette.com/auth/success?token=<accessToken>
   Set-Cookie: refreshToken=...
   ↓
9. Frontend extracts token from URL, stores in memory, redirects to app
```

### Account Linking Strategy

**Scenario 1: New OAuth User (Email Doesn't Exist)**
- Create new User: { email (from OAuth), firstName (from OAuth), passwordHash: null }
- Create OAuthProvider: { userId, provider, providerId, email }
- User can only login via OAuth (no password)

**Scenario 2: Existing Email/Password User**
- User exists with passwordHash
- Link OAuth provider to existing account
- Create OAuthProvider: { userId (existing), provider, providerId, email }
- User can now login via email/password OR OAuth

**Scenario 3: Existing OAuth User (Same Provider)**
- OAuthProvider record exists
- Retrieve existing user
- Return tokens
- No new records created

**Scenario 4: Multiple OAuth Providers (Same Email)**
- User already has Google OAuth linked
- User signs in with Apple (same email)
- Link Apple OAuth to existing user
- User can now login via Google OR Apple

**Email as Unique Key:**
- Email must be unique across all users
- Multiple OAuth providers can share same email
- Account linking happens automatically based on email match

### Security Considerations

**OAuth-Specific Security:**
- State parameter: Use to prevent CSRF attacks (optional, Passport handles)
- Token validation: Verify OAuth tokens come from legitimate provider
- Email verification: Trust OAuth provider's email verification
- Account takeover: Email linking allows account takeover if OAuth email compromised
- Mitigation: Require email confirmation before linking (optional, V2 enhancement)

**Data Privacy:**
- Only request necessary scopes: email, profile (Google), email, name (Apple)
- Never request access to user's Google/Apple data beyond profile
- Store minimal OAuth data: providerId, email only

**Apple-Specific Security:**
- Private key storage: Store Apple private key securely (environment variable or secrets manager)
- Email privacy: Apple may hide user's real email (relay email like privaterelay@appleid.com)
- Handle missing email gracefully on subsequent logins

[Source: docs/architecture/security-and-performance.md#authentication-security]

### Apple OAuth Edge Cases

**Challenge 1: Email Only Provided Once**
- Apple provides email and name ONLY on first authorization
- Subsequent logins provide only providerId
- Solution: Store email in OAuthProvider record on first login
- Use stored email for account linking on subsequent logins

**Challenge 2: User Declines Email Sharing**
- Apple allows users to hide their email
- Backend receives no email or relay email
- Solution: Reject OAuth login if no email (or accept relay email)
- Document limitation: "Email required for account creation"

**Challenge 3: Name Structure**
- Apple returns name as object: { firstName, lastName }
- Google returns displayName or givenName
- Solution: Normalize to firstName only for MVP

### Error Handling

**OAuth-Specific Errors:**

1. **OAuth Provider Error**
   - Trigger: Google/Apple returns error in callback
   - Example: User denies consent
   - Response: Redirect to frontend with error param
   - Frontend URL: `https://app.bmadrecette.com/auth/error?error=access_denied`

2. **Missing Email from OAuth**
   - Trigger: Apple user hides email OR email not provided
   - Response: Return 400 Bad Request with message "Email required for account creation"
   - Alternative: Accept and create user without email (not recommended)

3. **Duplicate OAuth Provider**
   - Trigger: Same providerId already linked to different email
   - Response: 409 Conflict with message "OAuth account already linked to another user"
   - Rare edge case: User changes email in OAuth provider

4. **Account Linking Conflict**
   - Trigger: Multiple users with same email (should be impossible due to unique constraint)
   - Response: 500 Internal Server Error
   - Log error and alert developers

**Error Redirect Format:**
```
https://app.bmadrecette.com/auth/error?error=<error_code>&message=<url_encoded_message>
```

describe('AuthService - OAuth', () => {

        email: 'oauth@example.com',

      const result = await service.handleOAuthLogin(oauthPayload);

      // Assert
      expect(mockRepository.createWithOAuth).not.toHaveBeenCalled();
