# Story 2.7: Delete Recipe API

## Status
Draft

## Story
**As a** user,
**I want** to permanently delete recipes I no longer need,
**so that** I can keep my library organized and remove mistakes.

## Acceptance Criteria

1. DELETE /api/recipes/:id endpoint soft-deletes or hard-deletes recipe
2. Cascade deletion removes: recipe ingredients, steps, tags associations, photo records from database
3. Photos deleted from S3 asynchronously (queued job to avoid blocking response)
4. Authorization enforced: only recipe owner can delete
5. Returns 204 No Content on successful deletion
6. Returns 404 Not Found if recipe doesn't exist or unauthorized
7. Deletion logged for audit trail (userId, recipeId, deletedAt timestamp)

### Hard Delete vs Soft Delete Decision

**Hard Delete (MVP Recommendation)** [Source: AC 1, RGPD compliance]
- Permanently removes recipe from database
- Simpler implementation (no filtering deleted records)
- RGPD compliant: "Right to be forgotten" easily satisfied
- Cleaner database: No orphaned soft-deleted records accumulating
- Immediate effect: Recipe gone immediately

**Soft Delete (V2 Consideration)**
- Sets `deletedAt` timestamp, doesn't actually remove
- Allows recovery feature: "Undo" or "Recently Deleted" folder
- Complicates queries: Must filter `WHERE deletedAt IS NULL` everywhere
- Storage overhead: Accumulates deleted data over time
- Requires periodic cleanup job to hard-delete after 30 days

**MVP Choice**: Hard delete (simpler, meets AC, no storage bloat)

### Cascade Deletion Schema

**Recipe Deletion Cascades** [Source: architecture/database-schema.md, Story 2.1]
```prisma
model Recipe {
  id          String   @id @default(uuid())
  userId      String
  // ... other fields

  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  ingredients RecipeIngredient[]  // Cascade deletes
  steps       RecipeStep[]        // Cascade deletes
  tags        RecipeTag[]         // Cascade deletes
  photos      RecipePhoto[]       // Cascade deletes

  @@map("recipes")
}

model RecipeIngredient {
  id        String  @id @default(uuid())
  recipeId  String

  recipe    Recipe  @relation(fields: [recipeId], references: [id], onDelete: Cascade)

  @@map("recipe_ingredients")
}

// Similar for RecipeStep, RecipeTag, RecipePhoto
```

**Database-Level Cascade** [Source: PostgreSQL documentation]
- PostgreSQL foreign key constraint with `ON DELETE CASCADE`
- Automatic deletion propagation in single transaction
- More efficient than application-level cascading (fewer queries)

### S3 Photo Deletion Strategy

**Async Deletion Approach** [Source: AC 3]
```typescript
async delete(recipeId: string, userId: string): Promise<void> {
  // 1. Fetch recipe and photos
  const recipe = await this.recipesRepository.findById(recipeId);
  if (!recipe) throw new NotFoundException();
  if (recipe.userId !== userId) throw new ForbiddenException();

  const photos = await this.prisma.recipePhoto.findMany({
    where: { recipeId },
    select: { s3Url: true, thumbnailUrl: true },
  });

  // 2. Delete from database (cascade deletes photos table too)
  await this.recipesRepository.delete(recipeId);

  // 3. Queue async S3 deletion (don't block response)
  if (photos.length > 0) {
    this.queueS3PhotoDeletion(photos);
  }

  // 4. Log deletion
  this.logger.info({ userId, recipeId, event: 'recipe_deleted' });
}

private async queueS3PhotoDeletion(photos: { s3Url: string; thumbnailUrl: string }[]): Promise<void> {
  // Option 1: Use BullMQ/Bull job queue (robust, retry logic)
  // await this.photoCleanupQueue.add('delete-photos', { photos });

  // Option 2: Simple async (MVP simplification)
  setImmediate(async () => {
    for (const photo of photos) {
      try {
        await this.storageService.deleteFile(this.extractS3Key(photo.s3Url));
        await this.storageService.deleteFile(this.extractS3Key(photo.thumbnailUrl));
      } catch (error) {
        this.logger.error({ error, photo, event: 's3_deletion_failed' });
        // Don't throw - recipe already deleted from DB
      }
    }
  });
}
```

**Why Async S3 Deletion?** [Source: AC 3, performance best practices]
- S3 deletion can take 500ms-2s per photo (network latency)
- Recipe with 5 photos: 5-10 seconds blocking time
- User experience: Instant delete response (204 immediately)
- Trade-off: Eventual consistency (photos might exist briefly after recipe deleted)

**MVP Simplification**: If job queue adds complexity, use synchronous deletion (acceptable for MVP with few photos)

### Authorization Pattern

**Ownership Verification** [Source: AC 4, 6]
```typescript
async delete(recipeId: string, userId: string): Promise<void> {
  const recipe = await this.recipesRepository.findById(recipeId);

  if (!recipe) {
    throw new NotFoundException('Recipe not found');
  }

  if (recipe.userId !== userId) {
    // Option 1: Return 404 (more secure, doesn't reveal recipe exists)
    throw new NotFoundException('Recipe not found');

    // Option 2: Return 403 (more explicit, but reveals recipe exists)
    // throw new ForbiddenException('You do not own this recipe');
  }

  // Proceed with deletion...
}
```

**Security Consideration** [Source: OWASP best practices]
- Return 404 for both "not found" and "unauthorized" to prevent information leakage
- Prevents attackers from enumerating valid recipe IDs
- Consistent with Story 2.5 (Get Recipe) pattern

### Error Handling

**HTTP Status Codes** [Source: AC 5, 6, REST best practices]
- 204 No Content: Recipe deleted successfully (no response body)
- 401 Unauthorized: No JWT token or invalid token
- 404 Not Found: Recipe doesn't exist OR user not authorized
- 500 Internal Server Error: Database error or unexpected failure

**Prisma Error Handling**
- P2025: Record not found → 404 Not Found
- P2003: Foreign key constraint violation (shouldn't happen with cascade) → 500 Internal Server Error

**S3 Deletion Errors** [Source: Async deletion strategy]
- Network failure: Log error, don't block deletion (eventual consistency)
- Permission denied: Log error, schedule retry (cleanup job in V2)
- Object already deleted: Ignore (idempotent)

### Performance Considerations

**Delete Query Performance** [Source: Prisma optimization]
- Single DELETE query: `DELETE FROM recipes WHERE id = ?`
- Database triggers cascade deletes automatically (efficient)
- No N+1 problem (no loop through relations)
- Target: <100ms for recipe deletion

**S3 Deletion Performance** [Source: AC 3]
- Async deletion prevents blocking user
- Recipe with 10 photos: ~10 seconds S3 deletion time (parallel requests)
- User sees instant response (204 immediately)

**JWT Validation** [Source: Story 1.6 JWT implementation]

- Extract userId from verified token payload

- Backend doesn't need confirmation (trust authenticated request)
- V2: Optional "soft delete with recovery" for safety
